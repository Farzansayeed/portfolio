BhuKosh

Land records in India exist mostly as scans of handwritten registers in multiple Indian scripts. BhuKosh turns them into validated digital records where every AI-extracted value stays bound to the exact pixels it was read from — and every record carries a truth-assurance verdict computed from independently checkable signals, never the model's opinion.

01 — The problem with "the AI read it"

Reading is easy. Proving is the product.

01 · Evidence-bound AI

An extraction run's input hash is the SHA-256 of the exact bytes sent to the model. Replay any value: candidate → run (engine, prompt version, input hash) → document/page (hashes, sequence) → for vision runs, the cropped pixels the value was read from.

02 · Validation before humans

Five deterministic, versioned business rules run on every record; only anomalies — with plain-language explanations and linked evidence — reach a reviewer. Uncertain fields (confidence < 0.6 or unreadable) route to review automatically; they never enter the database silently.

03 · Two scores, honestly separated

Reading confidence answers "did we read the pixels right?" Truth assurance answers the harder one — "why believe it's correct?" — as a verdict from independently checkable signals. A VERIFIED record can still fail honestly when evidence contradicts it.

04 · Tamper-evident provenance

The audit trail is a hash chain enforced by database triggers — rows cannot be edited or deleted, and /audit/verify re-checks the whole chain. Exports are immutable snapshots with an evidence manifest.

05 · A real workflow, not a form

Claim locks (HTTP 423), optimistic versioning (HTTP 409), mandatory reasons for rejections, corrections, and reopens — one audited write path for every human decision.

06 · It learns from its reviewers

Human corrections are injected as few-shot guidance into future extraction prompts — and the loop is inspectable at GET /learning/hints: the exact lessons the engine carries, with the decision trail behind each one.

07 · Multilingual end to end

Reads any Indic script (verified live on Devanagari khatauni registers and Gujarati VF-6 forms), interface in EN / हिन्दी / ગુજરાતી, extracted values renderable into all three — original script always preserved as evidence.

08 · Runs anywhere

Identical code against a local offline Postgres (courts and tahsils with no internet) or a cloud deployment — selected by one environment variable.

02 — System design

One scan's journey.

  1. SOURCE Scans enter through a signed intake manifest — register ref, centre, device, per-page SHA-256 hash-of-hashes verification.
  2. EVIDENCE Documents are content-addressed by SHA-256; byte-identical re-uploads are rejected (HTTP 409). Pages get sequence + hashes.
  3. LAYOUT The vision engine reads the scan: per field — value, bounding box, confidence 0–1. Each box is cut into a content-addressed evidence crop.
  4. EXTRACTION 12 land-record fields, schema-locked JSON. Every run logs engine, model, prompt version, input hash.
  5. REASONING Five versioned rules validate: pattern sanity, area format, missing identity, unreadable fields, cross-record area jump > 25%.
  6. VERIFICATION A strict state machine: claim locks, optimistic versioning, every human decision versioned, reason-tracked, hash-chained.
  7. PROVENANCE Every decision emits an audit event in the same transaction; the chain is append-only by trigger, verifiable on demand.
  8. TRUSTED OUTPUT Immutable JSON/CSV exports with evidence manifests; OpenAPI for downstream LRMS/DILRMP consumption.

The state machine: INGESTED → EXTRACTED → VALIDATED → REVIEW_REQUIRED → VERIFIED → OFFICER_CERTIFIED, plus REJECTED / QUARANTINED exits and REOPEN. Current values are a projection of the append-only history — never an independent edit.

03 — Engineering decisions

Choices worth defending.

Multi-engine by default

Three engines ship (Gemini primary, OpenRouter MiniMax, Groq text path). The lineup wasn't taste — it was a bake-off: 11 free vision models scanned, top candidates tested against a real Gujarati VF-6 inheritance-form scan. MiniMax-M3 read it correctly in ~4 s; Gemma free models were quota-saturated; Groq's former vision model was retired upstream. A 429 storm on one provider never blocks extraction — switch engines and continue.

Two scores, not one

Most pipelines collapse "the OCR was confident" into "the record is correct." BhuKosh separates them deliberately: confidence is per-field, and document-level as the worst field — a record is as trustworthy as its weakest reading. Assurance is a composite verdict over rule outcomes, cross-record corroboration, document integrity, and human authority.

Audit chain in Postgres triggers

The append-only guarantee lives in the database, not app code: triggers serialize appends on a Postgres advisory lock, so concurrent actions can never fork the chain — even a buggy app can't rewrite history. Every decision emits its audit event in the same transaction as the change.

Duplicate & forged-scan detection

Every page carries a 64-bit perceptual hash (dHash); near-matches (≤ 6 bits different) catch re-scans that differ at the byte level. A Gemini forensic pass reports tamper signals and per-page verdicts — CLEAN / SUSPECT / LIKELY_FORGED — explicitly labeled decision support only; a human decides. Stamps, seals, and signatures are learned from VERIFIED+ records only — the AI learns what genuine documents look like from the corpus humans already certified.

Search in Postgres, not a search server

One term matches record ID prefix, village, khasra, and every extracted field value — executed entirely in Postgres on pg_trgm GIN indexes with similarity ranking. Spontaneous, per-keystroke fast, no extra infrastructure, graceful fallback when the extension is unavailable.

Honest architecture

The external LRMS/DILRMP registry cross-check renders as an explicit "adapter slot," never a faked lookup. Forensic verdicts are labeled decision support only. Records without confidence scores show honestly empty. The README carries an honest caveats section — public demo credentials (on purpose, for judges), shared free-tier quota, cold starts, prototype-level learning loop. A tool about trustworthy claims should model trustworthy claims.

05 — Reflection

What I'd do differently.

  • Calibrate the confidence. The engine self-reports a 0–1 confidence per field; first on the roadmap is validating that self-report against observed correction rates per band — trust the score only after it earns it.
  • Benchmark, not just demo. Accuracy claims are demo-verified, not benchmarked. An evaluation harness with labeled benchmark sets would make every future change measurable.
  • Real adapters, when there's something to adapt to. LRMS/DILRMP integration is deliberately an honest adapter slot today; direct integration needs a counterpart system to test against, and faking one would betray the project's own thesis.
